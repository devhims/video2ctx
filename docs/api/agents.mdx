---
title: "Use video2ctx from agents"
description: "Give an agent authenticated, source-linked video context with a published skill."
---

Start personal, low-to-moderate public YouTube requests with `youtube-ctx` on the user's machine. It routes text and metadata work to direct extraction, and visual questions to a transcript/storyboard scan that uses local FFmpeg only when exact-frame verification is necessary. Use `video2ctx-platform` for production or cloud-backed search, transcripts, video and channel metadata, caption tracks, comments, end screens, playlists, account data, and recurring workflows; continue through its data branch automatically if direct access fails. The platform skill uses the public `@video2ctx/cli` package for browser-based device login and production API calls without placing a secret in the prompt.

<Steps>
  <Step title="Discover narrowly">Search for videos or resolve the relevant resource in your own application before requesting deeper datasets.</Step>
  <Step title="Fetch only needed context">Retrieve metadata first, then transcript, comments, channel information, or playlist items according to the task.</Step>
  <Step title="Preserve provenance">Keep video IDs, source URLs, transcript timestamps, fetch times, partial flags, and warnings with the text given to the model.</Step>
  <Step title="Return verifiable evidence">Link claims back to the video and timestamp instead of treating model output as the source.</Step>
</Steps>

Install the hosted CLI with `npm i -g @video2ctx/cli`. It keeps its revocable session in private local configuration. An existing `VIDEO2CTX_API_KEY` remains a non-interactive fallback and takes precedence. Bound query length, response size, continuation depth, and the number of fresh operations an agent can initiate.

Use the platform skill's data branch only for stateless provider reads, usage, and account identity. Projects, trends, research, and other composite workflows are outside its contract. Use its monitoring branch only for monitors, notifications, and delivery preferences.


## Submit a message

`POST /v1/agent` requires a message and your usual authorization. For a new session, send:

```json
{ "message": "Research five videos about durable agents" }
```

For a follow-up, include the `sessionId` returned by the previous request:

```json
{
  "message": "Compare the first two videos",
  "sessionId": "a54e2d7b-bc42-4c4f-b81d-6b64e92836d8"
}
```

Each accepted submission starts a new run, even if the
message is identical. Save the `sessionId` and `runId` from the `202` receipt to
retrieve existing work. If the receipt is lost, check **Dashboard → Sessions** or
`GET /v1/agent/sessions` before resubmitting. Sending the message again may create
another run and incur another charge.

Internal queue retries reuse the saved run ID to avoid duplicate execution.

If a session catalog update fails after admission, the error includes
`error.details.sessionId` and `error.details.runId`. Use those IDs to retrieve the
admitted run.

## Session identifiers and dashboard

Agent receipts, run results, session lists, and session details return `sessionId`.
Continue an existing session by sending `sessionId` in `POST /v1/agent`.
Agent responses expose `agentMessageId`, replacing `assistantMessageId`. The ID value
stays the same for existing runs. Use it as `parentMessageId` to branch from that answer.
The older `conversationId` request field remains a deprecated alias; if both fields
are supplied they must match. Responses no longer return `conversationId`, including
`responseFormat=legacy`. Update clients that read that response field. Existing UUIDs,
polling URLs and stored session history remain valid.

Accounts with agent access can open **Sessions** in the dashboard to search their
own sessions and read messages, answers, cited sources, warnings, and run failures.
The menu and page use `GET /v1/agent/access`, which applies the same runtime flag,
access mode, and current verified-email allowlist as the agent API. A successful check
returns `{ "enabled": true }`; denied accounts receive 403 and disabled or unavailable
checks receive 503. Every session and run read checks access again. Admin access does
not grant access to another account's sessions.

## Dashboard chat and live activity

Accounts that pass the agent access check can start sessions and send follow-up
messages from **Dashboard → Sessions**. Follow-ups use the same session and the
existing conversation history. The composer waits for the active run to finish.
If sending cannot be confirmed, the composer links to Sessions to find the submitted
run. Choosing **Send as new run** submits another message and may incur another charge.

Follow-up memory includes source-linked video metadata from completed ancestor turns, even when the earlier answer did not mention it. Snapshots can include the title, channel, view count, duration, availability, caption status, and keywords. Memory keeps up to eight videos and 8,000 serialized metadata characters per turn, within the existing eight-turn and 64,000-character model-memory limits. It excludes bot challenges and private provider payloads, and stays within the selected session branch.

Remembered metadata remains historical. The agent can cite it without repeating the provider operation or its evidence charge, or request a refresh when current data is needed. A successful current-run lookup supersedes the remembered snapshot for that video. If refresh fails, the earlier value remains available with its timestamp. Older runs that did not store a fetch time use the evidence recording time, explicitly labeled as such. Metadata reuse does not count as new transcript coverage.

To watch an admitted run, request:

```http
GET /v1/agent/{sessionId}/runs/{runId}/events
```

The authenticated endpoint returns `text/event-stream`. A `snapshot` event
contains `{ run, phase, tools }`. `run` has the compact run response shape;
`phase` is `queued`, `classification`, `research`, `finalization`, or the terminal
status. Each tool includes its name, status, start/end times, public input
arguments, and an evidence summary when available. Raw provider payloads,
continuation tokens, diagnostic captures, and model reasoning are excluded.

Completed visual tools can include saved image previews. Frame calls expose
`tools[].output.frames`; storyboard inspection calls expose
`tools[].output.storyboard.sheets`. Each preview includes `collectionId` and
`assetId` for `GET /v1/agent/frames/{collectionId}/{assetId}`. Storyboard sheets
also include the first and last sampled timestamps, grid dimensions, sample count,
and interval. The dashboard displays these images in an expandable gallery.
Metadata-only storyboard calls report `storyboard.mode: "metadata"` with no
images and appear as **Storyboard metadata**. Older inspection calls may have
no saved previews. Preview links work without authentication, remain available
until account deletion, and do not trigger extraction or additional credits.

Replace the previous snapshot instead of appending it. The first snapshot on
any connection restores the saved state, so completed sessions retain their tool
trace. Active connections rotate after roughly 25 seconds; reconnect on EOF
while the run is pending or running. `heartbeat` events keep idle connections
active. An `unavailable` event means live observation was interrupted; it does
not mean inference failed. Reconnect to the same run to resume observing it.
Disconnecting never cancels or restarts the durable run, and observing it does
not add a run charge.

Progress and tool results stream during execution. The answer is delivered after
finalization and validation, in the terminal snapshot. This endpoint does not
stream unvalidated model tokens.


## Stored extraction diagnostics

To inspect storyboard and frame extraction attempts for a run you own, request:

```http
GET /v1/agent/{sessionId}/runs/{runId}?include=diagnostics
```

`diagnostics.extractions` contains attempt summaries linked by `toolCallId` and
`extractionId`. Each summary records the container slot, attempt number, duration,
HTTP status when available, outcome, and safe stage details such as player profile,
media format and resolution, WebP conversion, retries, and FFmpeg exit code.
These records remain available when extraction or subsequent visual analysis fails.

The `capture` field explains how much detail reached the Worker:

- `available`: a valid diagnostic envelope was received. Invalid individual events are dropped.
- `missing`: a decoded response omitted diagnostics, such as an older container or a busy response.
- `invalid`: the diagnostic envelope or fallback response could not be decoded or validated.
- `unavailable`: no decodable diagnostic response was captured, including transport timeouts.

Each attempt retains at most 64 events, prioritizing the first 16 and latest 48;
`droppedEvents` counts omitted events. Storage is capped at 64 attempts or 256 KiB per
run. `diagnostics.extractionDiagnosticsTruncated` is true if another attempt could
not be stored. Normal compact responses, live activity, evidence, and model inputs
exclude these records. Legacy responses expose the equivalent `extractionDiagnostics`
and `extractionDiagnosticsTruncated` fields.

Stored summaries exclude raw error messages, stderr, URLs, headers, credentials,
and image bytes. Capture is best effort: a container crash or lost response can leave
only a Worker attempt summary. Both the Worker and container images must be deployed
for full detail. Historical runs cannot be backfilled. The dashboard does not yet
have a dedicated extraction-diagnostics panel; use the authenticated run endpoint.
